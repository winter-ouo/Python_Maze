
# 🧭 Python 期末專案執行企劃書

**專案名稱：** 2D迷宮：RDFS 自動生成與雙演算法動態互動系統

**開發團隊：** 四人專案小組

**開發環境與成本：** 本地端運行，無須 API Key，適用於一般文書筆電（以 ASUS X515 為測試基準）。

## 一、 專案概述與核心目標

本專案旨在透過 Python 實作一個結合圖論演算法、即時數據統計與遊戲互動的 2D 像素風視覺化系統。系統採用隨機深度優先搜尋（RDFS）演算法自動生成具備唯一解的迷宮，並動態展示不同尋路演算法（A* 與 BFS）在迷宮中的探索過程。

專案採用「折耦優化架構」進行平行開發。使用者可透過滑鼠調整地圖結構、利用鍵盤控制角色，並在演算法尋路過程中即時改變環境，測試演算法的重規劃（Re-routing）表現。整體設計兼顧軟體工程的職責分離（SoC）原則，同時確保學生筆電的執行效能。

---

## 二、 核心互動模式設計

主畫面採用 OpenCV 進行像素級渲染，並區分為單/雙畫布（Dual-Canvas）結構，支援以下三種互動模式：

1. **【模式 A：自製迷宮模式】** 在演算法啟動前，使用者可利用滑鼠左鍵在 OpenCV 畫布上點擊或拖曳，即時將通道（`0`）修改為牆壁（`1`），手動調整迷宮結構。
2. **【模式 B：人機競速模式】** 畫面區分為左右雙畫布。左側由 AI（A* 演算法）依據固定時間步長自動尋路，右側由使用者透過鍵盤 `W`, `A`, `S`, `D` 鍵手動控制角色。雙方在相同速度基準下比拼抵達終點的時間。
3. **【模式 C：動態地圖干擾模式】** 在 AI 尋路過程中，若使用者透過滑鼠即時放置牆壁阻擋當前路徑，系統將觸發重規劃邏輯。演算法必須即時以當前座標為起點重新計算路徑，並記錄重規劃效能指標。若被完全封死則跳出無解提示。

## 三、 專案目錄結構與模組分工

為了實現 GitHub 提交零衝突（Zero Conflict），專案採用扁平化的解耦架構。開工初期優先定死 `maze_model.py` 骨架檔案，確保各模組對接流暢。

```text
Python_maze
│
├── README.md
├── .gitignore              # 排除 __pycache__ 與本地設定
│
└── src
    ├── __init__.py
    ├── maze_model.py       # 共同協定：定義迷宮與玩家資料結構、防禦檢查
    ├── maze_generator.py   # 隊員 A：專注 RDFS 核心生成與地圖優化
    ├── path_astar.py       # 隊員 B：專注 A* 演算法核心實作
    ├── path_bfs.py         # 隊員 C：專注 BFS 演算法核心實作
    ├── renderer.py         # 隊員 D-1：專注 OpenCV 畫面渲染與緩衝優化
    └── main.py             # 隊員 D-2：專注遊戲狀態機、統計收集與動態節流

```

### 1. 【資料模型模組】（全體共同協定）

* **負責檔案：** `src/maze_model.py`
* **開發核心：** 建立基礎資料模型，不包含任何 OpenCV 繪圖或演算法邏輯。
* `Maze` 類別：封裝 NumPy 矩陣、起終點座標、寬高資訊。
* `is_valid_move(row, col)`：集中管理邊界越界防護與牆壁實體碰撞檢查。
* `get_neighbors(pos)`：回傳給定座標上下左右鄰近的可通行位置，供尋路演算法調用。
* `move_player(current_pos, direction)`：接收 WASD 方向，計算並回傳碰撞檢查後的新玩家座標。
* `copy()`：提供深拷貝功能，供重規劃或狀態模擬時不影響原地圖資料。
* `reset()`：清除所有走訪痕跡與動態牆壁，將地圖還原至初始生成狀態，方便多次重複測試。



### 2. 隊員 A：【RDFS 地圖生成模組】

* **負責檔案：** `src/maze_generator.py`
* **開發核心：**
* **RDFS 自動生成：** 運用 NumPy 建立二維矩陣，支援使用者選擇 11×11 / 21×21 / 31×31（預設）等奇數尺寸。利用 Stack 紀錄軌跡，隨機走訪遇阻礙觸發回溯，確保生成完美迷宮。支援隨機「種子（seed）」參數以實現地圖可重現性。
* **開放度參數化（Openness）：** 接收開放度參數，於迷宮生成後隨機打通一定比例的內牆，製造局部開放空間與多重路徑，以顯現 A* 與 BFS 的效能差異。


* **介面規範：** `def generate_maze(w, h, openness: float, seed: int = None) -> Maze`

### 3. 隊員 B：【A* 啟發式尋路模組】

* **負責檔案：** `src/path_astar.py`
* **開發核心：**
* **啟發式搜尋：** 實作 A* 核心公式。啟發式函數採用曼哈頓距離。調用 `maze.get_neighbors()` 獲取節點。


* **介面規範：** `def solve_astar(maze: Maze, start: tuple, end: tuple) -> tuple[list, list, bool]` *(最終路徑, 走訪歷史, 是否有解)*

### 4. 隊員 C：【BFS 對照組尋路模組】

* **負責檔案：** `src/path_bfs.py`
* **開發核心：**
* **BFS 演算法：** 實作廣度優先搜尋，利用佇列（Queue）實現逐層擴散的盲目尋路機制，作為 A* 的效能對照組。


* **介面規範：** `def solve_bfs(maze: Maze, start: tuple, end: tuple) -> tuple[list, list]` *(最終路徑, 走訪歷史)*

### 5. 隊員 D：【雙緩衝渲染引擎與狀態機總管】

* **負責檔案：** `src/renderer.py` 與 `src/main.py`
* **開發核心：**
* **渲染分離（renderer.py）：** 實作雙緩衝機制。明確定義以下三大核心介面，杜絕畫面閃爍：
* `draw_single(maze, path, player_pos, visited)`：用於模式 A、C 的單畫布渲染。
* `draw_dual(left_state, right_state)`：利用 `np.hstack` 進行水平拼接，用於模式 B 的左右雙畫布對比。
* `update_display(canvas, delay)`：統一封裝 `cv2.imshow` 與 `cv2.waitKey`。


* **流程與統計控制（main.py）：** 管理當前狀態機（模式 A/B/C）。利用時間戳控制 AI 步進與玩家移動頻率一致（例如每 100ms 更新一次邏輯），並將 OpenCV 刷新率固定於 30ms。
* **中央統計與節流：** 統一收集所有數據（走訪格子數、重規劃次數、每次耗時等），避免數據分散。針對滑鼠放牆事件進行節流處理（Debounce），防範短時間連續點擊導致系統頻繁執行重規劃而崩潰。

## 四、 核心安全與防護邏輯設計

1. **中央化防禦：** 所有越界與碰撞檢查統一收攏於 `maze_model.py` 的 `is_valid_move` 函數中，消除各模組各自編寫判斷式所產生的漏洞。
2. **重複走訪防護：** 演算法尋路時，已探索節點一律存入 Python `set` 集合，防止重複加入佇列引發無窮迴圈。
3. **執行緒防衝突：** OpenCV 渲染與 Matplotlib 繪圖完全採取**時間序列隔離**。主迴圈進行時專心使用 OpenCV，當視窗關閉、遊戲結束後，主程式才調用 Matplotlib 產生結算圖表。

## 五、 GitHub 同步開發工作流 (Workflow)

1. **骨架先行協議：** 開工第一天由團隊共同完成並提交 `maze_model.py` 的基礎 Class 宣告（含 `get_neighbors` 與 `is_valid_move` 骨架）。
2. **目錄隔離制：** 程式碼統一置於 `src` 下，各組員嚴格遵循「僅編輯自身負責檔案」原則，開發期間透過 Mock 矩陣進行單元測試。
3. **最終合併：** 專案後期由隊員 D 於 `main.py` 中透過 `import` 匯入其餘模組，串接資料流與事件監聽。

## 六、 預期成果與統計指標

1. **視覺化呈現：** 輸出流暢、無閃爍的 2D 像素風視窗，動態展示 AI 探路軌跡與玩家控制角色的移動。通關後高亮顯示最終正確路徑。
2. **量化數據圖表（遊戲關閉後顯示）：**

* **圓餅圖（Pie Chart）：** 分析 BFS 尋路過程中的「正確路徑格子數」與「無效死胡同格子數」之比例。
